# 扫描服务自动恢复

扫描由网页预览、二维码识别、IMU、底盘里程计、局部融合、草稿采集和网页桥共同完成。预览有画面不代表定位识别服务在线。

`bash scripts/start.sh` 会检查网页并启动扫描依赖。已有网页进程不会跳过传感器服务。各依赖通过本项目托管器运行，优先使用 systemd 用户服务，退出后自动重启并退避；手动停止会禁用自动拉起。查看进程托管状态：

```bash
python3 scripts/service_manager.py status all
```

进程活着不等于传感器数据合格，实际就绪状态仍以网页/ROS数据心跳为准。

未标定横移、IMU/里程计中断、传感器时钟回退会使局部轨迹失效。融合监督器等待允许的停放模式、连续新鲜输入和车辆静止后，回收自己的输入适配器和EKF，重新校零并生成新定位原点。旧的运动轨迹不会被补造，也不会把未标定横移当作有效里程计。

恢复后扫描自动保存旧段，并在新原点下继续新一段。相同原点的重复时间戳不会重复写入；过期原点的迟到帧会丢弃。事务校验失败不会留下空记录。单段达到10000帧时也会自动另存继续，避免长期采集耗尽单段容量。

页面区分摄像头预览和定位识别，显示等待IMU、等待静止校零等实际原因；恢复换段后只跟随正在采集的扫描，打开历史记录时不会抢走选择。

当前 legacy 里程计仍不支持未经标定的横移；恢复采集需切回普通停车模式并保持静止完成校零。自动恢复结果保持草稿属性，不能升级为正式导航验收数据。

## 本次验证

构建和TypeScript检查通过。融合及恢复34项、托管器16项、传感器状态10项、界面9项测试通过；后端覆盖原点换段、事务回滚、后端重启续采、单段容量上限。

实机受控退出识别runner后，托管器自动拉起新PID并重新识别B000，见 `logs/scan-service-recovery-check.json`。真实融合输入中断后经历INVALID、CALIBRATING、PROVISIONAL，epoch变化，旧输入/EKF进程退出，见 `logs/fusion-auto-recovery-check.json`。测试过程中未发送底盘运动指令。
