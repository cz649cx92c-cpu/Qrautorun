### 前进、倒车、转向、横移

现有定义：车体 `4t4d=6 / crab=8 / neutral=2`；轮速转角命令 `4t4d=5 / crab=7 / neutral=2`。前后行驶使用带符号速度，原手柄已有倒车转角反号处理。正常4t4d实际采用四轮转向，是否可按标准前轮阿克曼建模还需确认轴距与后轮策略。

`controlxbox/fw_mini_headless_gamepad.py` 的 `_normalize_crab_target` 与 `_build_steering_command` 明确支持纯横向速度转换为±90°轮角和轮速；停车原地转轮也有现有入口。**这是源码支持情况，本次未进行90°实体到位或横移测试。** 后续导航只能复用上述原Topic并按停稳→切轮→新鲜四轮反馈确认→横移→停稳→恢复到位顺序实现，不能以固定等待时间当实体到位证据。

手柄已有A/B/X/Y模式切换、RT发送许可、低中高档、速度限幅、斜率限制和手柄断连清零逻辑。保留原程序；原ROS2 CAN驱动没有查到独立命令看门狗、命令来源互斥或速度限幅逻辑，固件超时停车需实测确认。后续需新增独立导航控制权仲裁而不是多个节点同时发原命令。

### 反馈问题：实体接入前必须解决

1. 原驱动接收 `ctrl_fb_y_linear` 使用 `/100`，而发送侧与手柄解码为 `/1000`，存在横向反馈缩放差异。不能直接将此反馈用于EKF。本次没有改原驱动，后续应通过原四轮反馈和实测确认选择独立校正适配方式。
2. `ChassisInfoFb` 将不同CAN帧聚合成一个对象，并在车体控制反馈帧到达时发布。整包时间戳不能证明各轮角和IO字段都新鲜，需要原始帧/独立反馈时效证据，才能做实体安全到位判断。
3. 一次实际反馈：车体与轮控原档位均为1（park），vx=0、vy=0、角速度=0；四轮角度约 `53.9,-54.2,-54.3,54.0` 度。角度符号可能包含各轮安装方向，**不得据此假设同号±90°就是全部到位**。
4. 现有 `/odom` 没有横移积分、有效噪声协方差，不直接复用为融合输入；后续新适配里程计必须支持body vx/vy，确认各轮速度与角度方向后再转换。
